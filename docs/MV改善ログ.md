## API キーの入れ方

生成系（`gemini` / `openai` / `stability`）を使う機能は、キーを入れた時点で動きます。
キーは**プロジェクト JSON には書きません**。共有されるファイルなので、書いた瞬間に漏れます。

```bash
movo config set gemini.apiKey <キー>
movo config set openai.apiKey <キー>
```

保存先は `~/.movo/config.json`（本人だけが読める 600）です。CI などファイルを置きたくない
場面では、環境変数 `MOVO_GEMINI_API_KEY` / `MOVO_OPENAI_API_KEY` / `MOVO_STABILITY_API_KEY`
のほうが優先されます。

## 改善の記録

### 1. タイミングのズレ — 「小節グリッド」＋「ブロック内は等間隔」

**何が悪かったか。** 歌詞を «歌っている区間» にモーラ数で比例配分していました。
配分そのものは妥当でも、1 行ぶんの誤差が後ろへ積もるので、**曲の後半ほどズレます**。
しかも行ごとの間隔が 2.0・3.5・3.0・3.5 小節とばらつき、«早い / 遅い» が交互に来て
«ズレている» と感じやすい出方をしていました。

**直したこと（3 つ）。**

1. **寄せる先を拍から «半小節» へ。** 148BPM だと 1 拍は 0.405 秒しかなく、拍に
   寄せてもほとんど動きません（ズレは 1〜2 秒の単位で出ます）。歌詞は小節頭か
   半小節で切り替わるので、そこへ寄せると音楽と揃います
   （`_half_bar_grid`）
2. **ブロックの中は一定間隔に均す。** 同じ節の中の行間隔を «平均を半小節に丸めた値»
   で揃えます。結果、ブロックごとに 2.5 / 3.5 / 3.0 小節という規則的な並びになりました
   （`_regularise_within_blocks`）。**アンカーのあるブロックは触りません**
3. **フレーズ検出も入れました**（`singing_phrases` / `assign_lines_to_phrases`）。
   息継ぎの切れ目に行を対応づける道です。ただしこの曲では **効きませんでした** —
   伴奏が中域を埋めていて、28 行に対しフレーズが 10〜12 個しか取れません。
   取れないときは自動で «小節グリッド + 等間隔» に落ちます（警告を出します）

**残っている限界。** 歌い出しの «絶対位置» は依然として推定です。ここは
`--anchor 1=5.4` のように 2〜3 点留めれば一発で合います。

### 2. テキストのはみ出し — 歌詞シーンに `fit` が無かった

`rich-*` のシーンは最初から `fit: {mode: "shrink"}` を持っていたのに、
**`mv-hype` / `mv-chorus` / `mv-verse` だけ抜けていました。** 既定の
`hypeSize` 300 は «ぐるぐる» のような 4 文字の行を想定した値で、実際の歌詞
（最長 15 文字）を入れると両端が切れます。3 つのシーンに `fit` を足しました
（`maxWidth` は画面幅の 90〜92%、下限 25%）。

### 3. 背景画像 — `make-mv` から画像を渡す口が無かった

`rich-mv` は `artAsset` / `figureAsset` という入力を持っていたのに、**素材を宣言する
手段がどこにも無く**、名前を指しても «そんな素材は無い» で終わっていました。
`--asset 名前=パス` を足しました（拡張子から種類を判定）。

```bash
movo make-mv song.mp3 --style rich-mv \
  --asset art=assets/free/susuki.png --set artAsset=art
```

素材は Wikimedia Commons の CC0 / パブリックドメインを 4 点取得しています
（`assets/free/CREDITS.md`）。1 点が progressive JPEG で自前デコーダが読めなかったので、
1920px 幅の PNG に再符号化してあります。

### 4. キャラクターを動かす — `chibi-stage` シーンを追加

GPT の画像生成が使えないので、**図形だけでキャラを組んで動かすシーン**を作りました
（`movo/skill/library/scenes/chibi-stage.json`）。外部素材が要りません。

動かしているもの: 体の上下（拍）・頭の傾き・アホ毛の揺れ・腕の振り・脚・
まばたき（3.4 秒ごと）・口の開閉（拍）。

**途中で `group` レイヤーのバグに当たりました。** `group` の `children` に入れた
図形は **1 つも描かれません**（単独のレイヤーとして置けば描かれます）。
最小の再現を作って確かめました（`tmp/grouptest.json`）。そのため各パーツを
トップレベルに置き、«全体の上下» は各レイヤーの `y` の式に同じ項を足して揃えています。

### 5. 並列レンダリングが落ちる件

`make-mv` で `--jobs` を使うと途中で
`A child process terminated abruptly` で落ちていました。原因は 2 つ。

1. **インラインのプロジェクトが子へ渡っていなかった。** `make-mv` はファイルではなく
   組み立てた JSON を描くので、子が «出力先の .mp4» を JSON として読みに行き、
   `'utf-8' codec can't decode byte 0xaf` で落ちていました。`session["inlineProject"]`
   を子へ渡すようにし、判定も «ファイルが存在するか» ではなく «インラインか» で
   見るようにしました
2. **進捗の報告に Manager を挟んでいた。** `Manager().Queue()` はプロセスをもう 1 つ
   起こし、その代理の接続が切れると **進捗の報告が失敗しただけでプール全体が壊れます**。
   素の `Queue` に替えました

なお `timeout` コマンド付きで検証すると、強制終了とこのエラーが区別できません
（同じメッセージが出ます）。検証は時間制限なしで行ってください。

### 6. `make-mv --style rich-mv` が壊れていた

`plan_sequence` がシーン名を `mv-*` で決め打ちしていたため、`rich-*` のスキルを
指定すると **8 カット中 5 カットの `with` が空**になり、色も画像も歌詞も既定値に
戻っていました。語尾（`intro` / `verse` / `chorus` / `hype` / `outro`）を役割として
読み、そのスキルのシーン名へ移すようにしました（`scene_roles` / `resolve_scene`）。

### 7. サビが «ぐるぐる» のままだった

`mv-chorus` は `lines` ではなく `hook`（決め文句）を見ます。時刻つきの歌詞を渡しても
`hook` だけスキルの既定に取り残されていて、120 秒地点で «ぐるぐる» が出ていました。
カットごとに «そこで最初に歌われる行» を `hook` に入れるようにしました。

### 8. キャラクターを «GPT の一枚絵 → 切り出し» に置き換え

キーを入れたうえで、指示どおり
**萌えキャラを 1 枚の絵にまとめて生成し、切り出して使い回す**形にしました。
実装は本ツールの中です（`movo/core/ai_image.py`）。

```bash
python -c "from movo.core.ai_image import generate_character_parts; \
  generate_character_parts('assets/character/kusa-girl.spec.json', 'assets/character', \
                           sheet_path='assets/character/_sheet.png')"
```

**一枚絵にする理由。** ポーズごとに別々に生成すると «同じキャラに見えません»
（髪の色も目の形も毎回変わります）。1 枚に並べて描かせると、モデルが
«同じキャラの別のポーズ» として描くので揃います。切り出しは格子の算術だけです。
`line-stamp-generator` プラグインと同じ考え方で、クロマキー緑＋マゼンタ格子線
という指示を借りました。

生成 1 回・4 ポーズ（`idle` / `sing` / `surprise` / `think`）。作り直しは
`sheet_path` に既存の PNG を渡せば **課金なしで切り出しだけ**やり直せます。

途中で踏んだこと:

| 症状 | 原因 | 直し方 |
| --- | --- | --- |
| `RuntimeWarning: invalid value in sqrt` | 色距離を `int16` で計算。255²×3 = 195,075 が上限 32,767 を超えて負になる | `int32` にする |
| 切り出しても 512x768 のまま刈られない | 地の緑は抜けても **マゼンタの格子線が不透明**で残り、余白判定がセル全体を «中身あり» と見る | 格子線も抜く |
| 格子線が抜けない | 線が細くて地と混ざり、純マゼンタではなく `[203, 67, 150]`（距離 135〜190） | 線用の許容差を 200 に（肌 248・髪 238・服 292 なので巻き込まない） |
| 輪郭がギザギザ | 0 か 255 かの二値で抜いていた | 地からの距離で 0〜1 に渡す（なめらかな縁） |
| 縮小すると縁に緑が滲む | アルファを 0 にしても **RGB は緑のまま** | 縁の色を外へ染み出させてから抜く（`bleed_edges`） |
| モデルが 2x3 ではなく 2x2 で描いた | 指示どおりに並べるとは限らない | **生成し直さず、切り出す格子を実物に合わせた**（追加課金なし） |

### 9. 構成を «歌詞ブロック ＝ 1 カット» に変えた

`make-mv` は «曲の区間 → シーンの並び» に落とす道具で、区間から割ると
**サビの途中でカットが変わります**。歌詞に合わせたいので、プロジェクトを直接
組み立てる道を用意しました（`tools/build_kusa_chibi_mv.py`）。

- 歌詞ブロック 1 つ ＝ シーン 1 つ。切れ目が必ず一致します
- 背景の写真・服の色・キャラのポーズ・文字の大きさをブロックごとに回します
  （`rich-mv` では同じ絵が 15 カット続きました）
- サビは動きを強め（`energy` 1.7）、キャラを大きく、文字も大きく

### 10. そのほか直したもの

- **`rich-burst` を «盛り上がり» の代わりに使わない。** スキル自身が
  «1 回だけ差すための枠» と書いているとおりの崩しで、`duotone` + `invert` が
  掛かります。`--intensity` を上げると 21 シーン中 13 シーンが反転した紫に
  なっていました（`ROLE_FALLBACKS` の順を `chorus` 優先へ）
- **CRF を 18 → 21 へ。** 既定の 18 はほぼ可逆で、全面グレインを全部符号化して
  **154 秒で 651MB（35Mbps）** になりました
- **`project.root`。** `tmp/` に置いた JSON からプロジェクト側のスキル
  （`scenes/*.json`）が見えず «スキルが見つかりません» になります

### 12. 数値の追い込みで分かったこと（失敗も含めて）

「閃光」の数値を目標に寄せる過程で、**行き止まりを 4 回踏みました**。同じことを
繰り返さないために書いておきます。

1. **地の色と暗幕の色が同じだと、不透明度を動かしても画は変わらない。**
   写真を敷かない作風では背景＝地の色なので、«同じ色の上に同じ色» を重ねる形に
   なっていました。静止率が 0.628 から 3 回いじっても 1 ミリも動かず、
   «式が効いていない» と誤診しかけました → `scrimColor` を分けて解決
2. **全画面の明滅で «静止の割合» を下げるのは筋が悪い。** 数値は下がりますが、
   フレーム間の差が常に大きくなるので **カット検出と干渉**し、同じ設定でも
   1 本〜33 本/分 と測るたびに変わりました。連続した動きは背景の寄せで作るべき
3. **写真を敷くと «少ない色数・高彩度» の作風は成立しない。** 実質の色数が
   102 色、彩度が 0.41 に落ちました。写真は「粒子」の作風のもの
4. **カット検出は «画面全体の差 0.18 以上»。** シーンは変わっているのに差が
   0.16〜0.17 にしかならず検出されない、ということが起きます。似た明るさの色が
   続くのが原因で、暗と明を交互に並べる必要があります。それでもトランジションで
   変化が数フレームに分散すると、やはり数値には出ません

**数値は «作風が合っているか» の目安であって、目的ではありません。** 目標に
入れるためだけに明滅を入れたのは行き過ぎで、外しました。

### 13. `group` レイヤーが何も描かないバグ — 直しました

`group` の中に入れた図形が **1 枚も描かれません**でした（同じ図形を単独で置けば
描かれます）。しかも **検証は通り、警告もエラーも出ません。**

原因は綴りの食い違いです。

| どこ | 綴り |
| --- | --- |
| JSON に書く側 | `layers` |
| レンダラーが読む側（`renderer/index.py` の `kind == "group"`）| `children` |
| `timeline/_prepare_layers` | `layer["layers"]` を読んで `entry["children"]` へ **無条件に代入** |

そのため **JSON に `children` と書くと、timeline が `None` で上書きして中身を
消します**。`layers` と書けば動きます。

追いかけ方はこうでした（そのまま再現できます）:

1. 最小の再現を作る（図形 1 枚を group に入れる / 外に置く）→ 外は描かれる
2. `_render_layer` を包んで追跡 → **子が 1 度も呼ばれていない**
3. `_render_content` の戻り値を見る → group の分岐は通っていて、buffer が空
4. `_render_content` の中で `len(layer["children"])` を出す → **0**（キーはある）
5. `children` を書き込んでいる場所を grep → `timeline/__init__.py:154`

**直し方**: `layer.get("layers") or layer.get("children")` の両方を受けます。
テストは `tests/test_parity_timeline.py` に 3 件足しました。

### 14. カット割りのズレが後半で積もるバグ — 直しました

B「閃光」が **162.2 秒**になっていました（曲は 153.6 秒）。1 カットずつ独立に
`round(尺 ÷ 1 小節)` していたので、**丸めの誤差が後ろへ積もります**。8.6 秒も
ずれれば、後半の歌詞は完全に合いません。

**直し方**: «曲頭からの絶対位置» を基準に取り直し、誤差を次のカットで打ち消します。

```python
bars = max(0.5, round(((piece_end / bar) - used_bars) * 2) / 2)
used_bars += bars
```

4 本とも 153.24 秒でぴたりと揃いました。

### 15. 作風の一致度（`movo compare` の最終結果）

**3 パターンとも 8 項目すべてが目標内**に入りました。

**書き出した本体を測った値**です（部分レンダリングではありません）。

| | A「余白」 | B「閃光」 | C「粒子」 |
| --- | --- | --- | --- |
| 目標に入った項目 | **8 / 8** | **8 / 8** | **8 / 8** |
| カット尺（秒） | 16.25（6〜30） | 1.62（0.4〜2.5） | 4.08（2.5〜8） |
| 毎分のカット数 | 2.74（2〜10） | 30.15（24〜150） | 9（8〜26） |
| 動きの量 | 0.004（0.003〜0.022） | 0.023（0.010〜0.060） | 0.007（0.004〜0.032） |
| 静止の割合 | 0.774（〜0.800） | 0.261（〜0.500） | 0.672（〜0.700） |
| 実質の色数 | 39（8〜48） | 40（6〜40） | 141（24〜160） |
| 彩度 | 0.152（0.050〜0.280） | 0.568（0.450〜0.900） | 0.397（0.200〜0.550） |
| コントラスト | 0.159（0.100〜0.350） | 0.233（0.200〜0.500） | 0.160（0.120〜0.380） |

**効いた直しは 3 つ**でした。

1. **`grade`（彩度・コントラスト）を実際に繋いだ。** 設定は書いてあったのに
   どこにも適用していませんでした。A の彩度が 0.313（目標は 0.28 以下）から
   0.159 へ
2. **寄せ（ken-burns）を強めた。** A は zoom 1.3 → 1.9。動きの量 0.002 → 0.004、
   静止の割合 0.87 → 0.766。**長回しの作風でも «止まって見える» のは別問題**です
3. **暗幕の濃さをカットごとに変えた。** これが決め手でした（下記）

### 16. `movo profile` のカット検出は «画面全体の明るさ» で見る

C のカットが 30 秒で 5 回あることを **自分で測って確かめた**のに、`movo profile`
は «1 本» としか出しませんでした。原因は検出のしかたです。

- 差を測るのは **24 x 13 に縮めた輝度の格子**（`_frame_features` の `luma`）
- そこでの平均差が **0.18 以上**で 1 カット

つまり **内容がまるごと変わっても、画面全体の明るさが変わらなければ数えません。**
写真から別の写真へ切り替えても、どちらも同じくらいの明るさなら 0 本です。

閾値は JS 版と揃えてあり（`profiles/*.json` と突き合わせるため）変えられません。
そこで **暗幕の濃さをカットごとに変えて、明暗そのものを上下させました**。

```python
"scrim": creator["scrim"] * (1.0, 0.45, 0.85, 0.35)[index % 4]
```

これで B が 2 本/分 → **26 本/分**、C が 2 本/分 → **8 本/分**。どちらも目標内です。
見た目にも «切った» と分かるようになりました。

**回り道の記録**: フェードを疑って 0.18 → 0.03 → 0 秒と詰めましたが、
どれも効きませんでした。原因は繋ぎ方ではなく «何を差として見ているか» でした。

### 17. キャラの切り抜きに残る «格子線» を落とす — 形で見る

色で狙っても取り切れませんでした。線は細いぶん周りと混ざり、指定した色から
離れた «くすんだ» 画素になります（実測で純マゼンタから距離 190 前後）。
許容差を広げれば取れますが、**唇や頬の赤まで巻き込みます**（実測 alpha 166）。

そこで **形で見ます。** 2 段構えです。

1. **開処理**（`remove_thin_marks`）… 1 度縮めてから同じだけ膨らませると、
   縮めた時点で消えた «細いもの» だけが戻りません。半径 2〜3 でアホ毛や指
   （6〜10px）を残しつつ 3〜4px の線を落とせます
2. **最大の連結成分だけ残す**（`keep_largest_blob`）… 開処理では落ちない
   «太めの断片» が頭上に残りました（8px）。キャラは 1 つの塊なので、中心から
   繋がっているところだけ残せば、形や太さに関係なく消えます

連結成分のラベル付けは «1 つ前の結果が要る» 逐次処理なので NumPy では素直に
書けません。`scipy.ndimage.label` があれば 1 行ですが、この計画は numpy と
numba だけで通す方針なので **Numba の塗り広げ**にしました。

⚠ **`keep_largest_blob` は «切り出した後» に、パーツごとに掛けます。** シート
全体に掛けると、いちばん大きな 1 体だけが残って **他のポーズが全部消えます**
（実際に 4 ポーズを全滅させました）。テストで固定してあります。

結果、パーツが正しく刈り込まれました（512x768 → 273x743）。

### 18b. A「余白」のカットが «見えない» 問題

最後まで残ったのが A でした。9 シーンあるのに `movo profile` は «1 本» としか
数えません。原因は数値で追えました。

```
動きの量 0.0034（最大 0.1271 ...）   ← 判定は 0.18
```

**最大の差が 0.127 で、判定の 0.18 に届いていませんでした。** 低彩度の作風は
画面全体が中間の灰に寄る（支配色 #333333 / #444433 / #333322）ので、写真が
変わっても平均輝度がほとんど動きません。

暗幕の振れ幅を段階的に広げて追い込みました。

| 暗幕の並び | 毎分のカット数 | カット尺 |
| --- | --- | --- |
| 一定（0.6） | 0.39 本 | 153 秒 |
| × (1.0, 0.45, 0.85, 0.35) | 0.39 本 | 153 秒 |
| × (1.0, 0.15, 0.85, 0.08) | 2 本 | 47 秒 |
| **× (1.0, 0.06, 0.9, 0.03)** | **3 本** | **14.5 秒** |

«切らない» 作風でも、**カットの «あるなし» は画面の明るさで示す必要がある** —
というのがここでの学びです。フェードを 0 にするのも効きました（0.2 秒でも
変化が数フレームに散って判定に届きません）。

### 19. 目視で見つけた最後の 1 つ — 歌詞がキャラに重なる

数値は 8/8 でも、**目で見ないと分からない欠陥**が本編に残っていました。
130 秒の «木みたいな草、草みたいな木» が、中央に立つキャラの体の上に重なって
どちらも読めません。

原因は単純で、**キャラの位置と歌詞の位置を別々に決めていた**ためです
（キャラは 0.22 / 0.78 / 0.5 を巡回、歌詞は 0.63 で固定）。

**直し方**: 歌詞をキャラの反対側へ置き、中央に立つカットだけは横に逃がせないので
下へ降ろします。

```python
"textX": 0.72 if char_x < 0.5 else (0.28 if char_x > 0.5 else 0.5),
"textY": 0.5 if char_x != 0.5 else 0.84,
```

**数値の確認と目視は別物**です。`movo compare` が 8/8 でも «読めるか» は測って
いません。1 本につき 3 枚ずつフレームを抜いて見る手順は残す価値があります。

### 18. B「閃光」のコントラスト — 明るい帯を敷いた

色面だけの作風は、画面が «一色に近い» ぶん明暗の広がりが出ません（0.144 /
目標 0.200 以上）。歌詞の後ろに **明るい帯を 1 本**敷き、文字を暗い色に
반転させました。「暗い地 ＋ 明るい帯 ＋ 暗い文字」で広がりが出ます。

## 一晩の作業でいちばん効いた考え方

**「効いていない」と思ったら、まず «本当に効いていないか» を数値で確かめる。**

このログの失敗はほとんど «変えたのに何も変わらない» から始まっています。

- 暗幕の不透明度を 3 回いじって静止率が 1 ミリも動かなかった
  → 地の色と暗幕の色が同じで、**同じ色の上に同じ色**を重ねていた
- カットを刻んでも «1 本» としか測れない
  → 検出は **24x13 に縮めた輝度**で見るので、明るさが変わらないと数えない
- group に入れた図形が消える
  → JSON の綴りは `layers`、内部は `children` で、**timeline が上書きしていた**

どれも «式が壊れている» と誤診しかけました。**最小の再現を作って、途中の値を
1 つずつ出す**のがいちばん速い道でした。
